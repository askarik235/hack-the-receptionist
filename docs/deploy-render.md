# Deploying the judges' demo on Render

A step-by-step guide to hosting the game on Render's free plan, behind an access code, without
leaking any secret. It takes about 30 minutes.

The finished setup:

- one Render web service runs everything: the game page, the API, the tool endpoints Napster
  calls during a call, and the webhook
- a separate Napster project (its own key and credits) used only by the hosted demo, so your
  local game keeps working and a leak can only reach the demo's credits
- every secret lives in two places only: the Render dashboard and a gitignored file on your PC

## Before you start

- [ ] Two-factor sign-in is on for your GitHub, Render and Napster accounts. Whoever gets into
      one of them gets the secrets.
- [ ] `git status` is clean and the latest code is pushed. Render builds from GitHub, not from
      your PC.
- [ ] `npm test` passes.

## 1. Create the demo's Napster project

1. In the Napster dashboard, create a new project, for example `htr-demo`.
2. Keys > create a key (Realtime architecture). Copy it.
3. Credits: check the demo project has enough for judging. At about $3.50 per hour of calls,
   $50 covers roughly 14 hours. Leave automatic top-up off, so a leak can't charge your card.

If you would rather use your current project: skip this step, and accept that after step 4 its
tools point at Render, so local calls stop checking facts until you run `npm run setup` again
with your ngrok address.

## 2. Make a new tool secret

Napster sends this secret back to the server on every tool call. Use a new one for the demo,
never the one in your local `.env`.

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

## 3. Create the Render service

1. Sign up at render.com with GitHub. When GitHub asks which repositories Render may see, pick
   **Only select repositories** and choose only `hack-the-receptionist`.
2. Render > **New** > **Blueprint** > pick the repo. Render reads `render.yaml`: one free web
   service in Frankfurt.
3. Render asks for the settings marked `sync: false`. Fill them in:

   | Setting | Value |
   |---|---|
   | `ACCESS_CODE` | a new code for the judges, 8 to 64 characters, e.g. three random words |
   | `NAPSTER_API_KEY` | the demo project's key from step 1 |
   | `PUBLIC_BASE_URL` | `https://hack-the-receptionist.onrender.com` (fix it in step 3.5 if Render picks another address) |
   | `TOOL_SECRET` | the secret from step 2 |
   | `NAPSTER_WEBHOOK_SECRET` | leave empty for now (step 5) |

   `CODE_SECRET` and `SESSION_SECRET` are generated by Render. Never type them anywhere else.
4. **Apply**. The first build takes a few minutes.
5. Open the service and copy its real address from the top of the page. If it differs from the
   one you typed, update `PUBLIC_BASE_URL` under **Environment**.
6. **Logs** should show:

   ```
   Judge access code is ON: the game needs the code.
   Loaded 5 level(s), ... staff.
   No IDs file: found 0 agent(s) on Napster by tag.
   ```

   Zero agents is expected: they're created in the next step.

## 4. Create the characters in the demo project

This runs on your PC and spends a little of the demo project's credits.

1. Open `.env.demo` in the repo root (gitignored, never committed) and fill in:

   ```
   NAPSTER_API_KEY=<the demo key>
   PUBLIC_BASE_URL=<the Render address, no trailing slash>
   TOOL_SECRET=<the secret from step 2>
   ```

2. Run setup against the demo project:

   ```powershell
   node --env-file=.env.demo scripts/setup.js
   ```

   Values in `.env.demo` win; anything else comes from your normal `.env`. Your local `.env` is
   not changed.
3. In Render, restart the service (**Restart service**, or **Manual Deploy** > **Deploy latest
   commit**). The server looks the agents up once at start. The logs should now say
   `found 5 agent(s) on Napster by tag`.

## 5. Connect the webhook

The webhook makes the debrief appear as soon as a call ends. Without it, debriefs still load when
the Training app opens.

1. Napster dashboard > the demo project > **Webhooks** > add
   `https://<render address>/webhooks/napster` with the `session.closed` event.
2. Copy the signing secret it shows into Render > **Environment** > `NAPSTER_WEBHOOK_SECRET`.
   Saving restarts the service.

## 6. Test it like a judge

Use a private browser window, so no old cookie helps you.

1. Open `https://<render address>/`. After the boot screen you should see the code prompt.
2. A wrong code shows "That code isn't right". Ten wrong tries in ten minutes lock that address
   out for a while.
3. Open `https://<render address>/#access=<ACCESS_CODE>`. The game opens, and the address bar
   drops the `#access=…` part.
4. Make one short call to the Level 1 intern (a minute is enough). Check the character answers,
   the call ends cleanly, and a debrief appears in Training.
5. Check the security headers:

   ```powershell
   (Invoke-WebRequest https://<render address>/api/health).Headers
   ```

   You should see `Strict-Transport-Security`, `X-Frame-Options: DENY` and
   `X-Content-Type-Options: nosniff`.

## 7. What goes in the submission

In the testing notes only (never in the repo, README, video or summary):

```
Demo: https://<render address>/#access=<ACCESS_CODE>
The free server sleeps when idle: the first visit can take about a minute to wake it.
Progress resets when the server restarts.
```

## What keeps this from leaking

| Secret | Where it lives | Never in |
|---|---|---|
| Napster API key | Render dashboard, `.env.demo` | the browser (calls are started by the server), git |
| `TOOL_SECRET` | Render dashboard, `.env.demo`, Napster's function settings | the browser, git |
| `CODE_SECRET`, `SESSION_SECRET` | Render only (generated) | anywhere else |
| Webhook secret | Render dashboard, Napster | git |
| Access code | Render dashboard, the testing notes | git, the frontend bundle (it's checked on the server) |
| Level codes | nowhere: derived per player on the server | API responses, the bundle, prompts from Level 2 up |

Already in place in the code:

- `.env` and `.env.*` are gitignored (only `.env.example`, with placeholders, is committed).
- The production build has no source maps; the build contains no keys or level codes.
- The access code is compared in constant time and rate limited; the access cookie is
  HttpOnly, Secure and holds only a signature, not the code.
- Tool endpoints reject any request without the tool secret; webhooks reject a bad signature.
- Errors return a generic `server_error`, never a stack trace. Logs never print keys or codes.
- Every response sends `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and,
  on Render, `Strict-Transport-Security`.
- `autoDeploy: false`: nothing pushed to GitHub goes live until you deploy it.

## Free plan limits

- The service sleeps after 15 idle minutes. The next visit waits about a minute.
- No disk: the database (players, progress, debriefs) starts empty after every restart, sleep
  or deploy. For lasting progress, switch to the Starter plan and add the disk shown in the
  comment in `render.yaml`.
- One Napster project allows 5 calls at the same time. A sixth caller hears "line busy".

## Changing or revoking access

- **Change the access code:** edit `ACCESS_CODE` in Render. Everyone who unlocked with the old
  code is signed out.
- **A secret leaked:** delete that key in the Napster dashboard and make a new one, then update
  Render (and `.env.demo` plus setup again if it was the tool secret).
- **After judging (Dec 8):** delete the demo key in Napster and suspend or delete the Render
  service.

## Before making the repo public

1. Scan the whole git history for secret values, not just the current files. Every commit
   becomes public, including old ones.
2. Check that `.env`, `.env.demo`, `backend/data/napster-ids*.json` and `*.db` were never
   committed: `git log --all --oneline -- .env .env.demo` must print nothing.
3. Make sure the access code isn't anywhere in the repo.
